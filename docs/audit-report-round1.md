## 3. API 安全与成本治理设计

### 3.1 当前状态

**缺失：**
- ❌ 无 `/api/interpret` 路由实现
- ❌ 无请求校验层
- ❌ 无速率限制
- ❌ 无成本追踪
- ❌ 无错误脱敏机制
- ❌ 无日志策略

### 3.2 设计方案（待实施）

#### A. 请求校验层

```typescript
// 校验规则：
// - chart: 服务端重算验证，不信任客户端派生结果
// - topic: 白名单枚举 ['overview', 'career', 'wealth', 'love', 'health', 'family', 'personality']
// - question: 长度 0-500，过滤控制字符
// - messages: 数组长度 0-10，每条 role + content 总长 ≤ 1000
// - 请求体总大小 ≤ 50KB
```

#### B. 速率限制层

```typescript
// MVP 阶段：内存限流（单实例）
// - 每 IP 每分钟最多 10 次请求
// - 每 IP 最多 3 个并发请求
// - 全局每日成本上限 ≤ 100 元
```

#### C. 成本控制层

```typescript
// - 单次请求 inputTokens ≤ 4000
// - 单次请求 outputTokens ≤ 2000
// - 每 IP 每日成本上限 ≤ 10 元
// - 记录：requestId, model, tokens, cost, latency, statusCode
// - 不记录：出生信息、姓名、完整 prompt、完整响应
```

#### D. 错误处理层

```typescript
// - 不向客户端泄漏：API Key、内部 prompt、供应商响应、完整堆栈
// - 统一错误格式：{ error: string, code: string, requestId: string }
// - 供应商超时：504 Gateway Timeout
// - 供应商 429：429 Too Many Requests
// - 输入校验失败：400 Bad Request
```

### 3.3 关键设计决策

1. **服务端重算命盘**：不信任客户端提交的 chart，防止伪造
2. **内存限流起步**：MVP 不引入 Redis，验证需求后再升级
3. **成本硬上限**：防止恶意调用导致巨额账单
4. **最小化日志**：只记录运营必需数据，不记录 PII

### 4.2 必须修改的内容

**隐私政策：**
1. 删除所有未实现功能的描述（账号、支付、短信、云端历史）
2. 明确说明 MVP 仅使用 localStorage 存储主题偏好和最近命盘
3. 明确说明是否将数据发送到第三方 AI 服务（如 DeepSeek/Kimi）
4. 说明数据处理地点（新加坡/中国/美国）和跨境传输情况
5. 提供用户删除 localStorage 数据的方法

**服务条款：**
1. 重新评估法律适用地区（新加坡 PDPA vs 中国 PIPL）
2. 由法律专业人士审查"100 万违约赔偿"条款的可执行性
3. 明确说明 MVP 当前提供的功能范围（仅排盘 + AI 解读）
4. 删除关于"水印追溯""反爬反训练"等未实现技术的宣称

### 4.3 新加坡市场合规要求

**PDPA（Personal Data Protection Act）关键点：**
- 数据收集需明确告知目的并获得同意
- 用户有权访问、更正、删除个人数据
- 数据保护官（DPO）需指定
- 跨境传输需确保接收方提供相当的保护水平
- 数据泄露需在 3 天内通知 PDPC 和受影响个人

**建议：** 在上线前由新加坡法律专业人士审查隐私政策和数据处理流程。

## 5. 排盘引擎审查

### 5.1 已确认的事实

- ✅ 引擎代码非空壳，存在完整排盘流程
- ✅ 10 个回归测试全部通过（盘面不变量、夏令时、钟表时间、立春边界、红鸾天喜、名人样本、时辰索引、日期合法性、同宫双四化、用词检查）
- ✅ 支持真太阳时、中国夏令时、四种闰月口径、晚子时换日、亮度流派切换、四化与飞星、十二神煞、格局判定

### 5.2 不能确认的事实

- ❌ 未与目标流派/权威排盘样例做全量差分验证
- ❌ 未证明所有年份、所有边界案例都符合目标用户所采用的排盘口径
- ❌ 测试覆盖的是内部不变量，不是第三方金标准验证

### 5.3 建议

1. **保留现有回归测试作为基线**：不可随意破坏
2. **建立金标准样例库**：30-100 个经人工核对的样例，覆盖节气/立春、闰月、子时换日、时区、经度、夏令时、未知出生时辰、年份边界、四化同宫等场景
3. **记录口径**：每个样例记录输入、流派配置、期望输出、参考来源/核验人
4. **分离事实与解释**：算法输出拆为"计算事实"和"流派解释"，用户可见页面标明采用的口径
5. **不承诺绝对准确**：不在没有验证的情况下宣称"100% 准确""科学预测"

## 7. 预算与执行顺序

### 7.1 精简方案（1,000-3,000 元）

适合验证一个小型 MVP，不足以一次性实现完整商业平台、专业法律意见和大规模数据标注。

**执行顺序：**

1. **第 1 阶段：基线与授权（先做）**
   - 修复 CLI 脚本类型错误
   - 整理许可证清单
   - 确认 MVP 可使用的内容来源
   - **工时：4-8 小时**

2. **第 2 阶段：单个 AI API**
   - 实现 `/api/interpret`
   - 供应商适配（DeepSeek/Kimi/千问）
   - 请求校验、超时、速率限制
   - 用量记录
   - **工时：16-24 小时**

3. **第 3 阶段：端到端 UX**
   - 接通现有 `InsightPanel`/`ChatPanel`
   - 改进 SSE 解析或统一为 JSON 响应
   - 完善 loading/error/retry
   - **工时：8-16 小时**

4. **第 4 阶段：隐私与试用**
   - 修订隐私政策和服务条款
   - 日志脱敏
   - 手工测试移动端
   - 邀请 5-10 位目标用户试用
   - **工时：8-12 小时**

5. **第 5 阶段：是否商业化的决策**
   - 根据需求、合规和成本数据决定是否做账户/支付
   - **工时：决策会议，不计入开发**

**总工时：44-68 小时（约 2-3 周）**

### 7.2 预算优先投向

✅ **优先：** API 可靠性、授权/隐私核查、关键测试、用户验证  
❌ **不优先：** 漂亮但不影响验证的复杂 UI、会员系统、微服务

## 10. 审计结论

**当前仓库的优势：**
- ✅ 已有前端入口和较丰富的排盘核心模块
- ✅ 一组有价值的回归测试
- ✅ 完整的排盘引擎（真太阳时、夏令时、闰月、格局判定）

**最大的缺口：**
- ❌ 缺少服务端 AI 闭环
- ❌ 缺少商业内容授权边界
- ❌ 缺少服务端安全/成本治理
- ❌ 缺少能证明目标排盘口径的金标准测试

**推荐策略：**
先把范围严格控制在"**排盘 + 一个主题的 AI 解读 + 复制报告 + 基础成本与安全控制**"。先让 5-10 位目标用户完成真实任务，验证他们是否理解并愿意再次使用，再决定是否引入数据库、账号、支付和更复杂的报告体系。

**不可跳过的发布闸门：**
1. ✅ 商业内容授权核查通过
2. ✅ `typecheck`、`test`、`build` 在实际环境成功
3. ✅ API 安全与成本限制通过
4. ✅ 隐私政策与真实数据流一致
5. ✅ 排盘样例经过人工核对

**未满足这些条件，不建议开放收费。**
